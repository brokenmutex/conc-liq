# Close-and-convert contract review — September 30, 2026

Status: analysis and proposal only. No `src/` change is made by this document
and nothing here authorizes execution. This is item 5 of
[`operation-gate-simplification-2026-09-30.md`](../plans/operation-gate-simplification-2026-09-30.md)
("Leave close and convert until last... its contract needs restating before
its gates can be pruned safely").

## 0. Method

Inventory built from `grep -rhoE "'paper_close_convert[a-z0-9_]*'" --include=*.ts src`,
which returns **223 distinct quoted string literals**. Of those:

- **8** are schema `kind` discriminators (e.g. `paper_close_convert_prestate_report_v1`),
  not failure codes.
- **3** are success-path stage labels written on completion (`..._reconciled`
  twice, once per generation of the completion function), not failures.
- The remaining **212** are genuine distinct failure/diagnostic codes. This
  document treats 212, not 223, as the denominator for "gate count," and says
  so wherever the two would give a different impression.

Every code was traced to its raising file/line and to the function that
contains it; every function was traced to its callers, up to the HTTP server
(`server.ts`), the preview generator (`deployments.ts`), and the worker loop
(`paper-operation-worker.ts`), to establish whether it is reachable from any
path a running system can currently take. The 13 files named in the task plus
the relevant parts of `store.ts` were read in full. Two more files outside the
named 13 turned out to matter and are cited where they do:
`src/deployments-paper-close-convert-gas-register.ts` and
`src/deployments-paper-close-convert-gas-sample.ts` (operator CLI tools, not
part of the HTTP/worker flow).

- `src/deployments/paper-close-convert.ts` — one of the 13 files named in the

**Of the 212 genuine failure codes, 87 (41%) are raised only inside this
unreachable v1/v2 machinery** (`replayPaperCloseConvert`, `closeConvertGasScopeV2`,
the four v2 gas-evidence functions, `prepareTrustedPaperCloseConvert`,
`completeTrustedPaperCloseConvert`, and the v1/v2 portions of
`paper-close-convert-model.ts`). The remaining 125 are live. **The "223
failure codes" figure the plan's table cites is therefore not the size of the
gate surface an operator's convert click actually passes through — it is
close to double that surface**, because it counts two generations, one of
which cannot currently run.

This changes the shape of the task. Pruning 87 dead codes is not a
simplification decision requiring an incident-by-incident argument under
section 3 of the plan — dead code protects no invariant currently in force,
because nothing reaches it. It is a deletion, not a simplification, and it
should be named as such rather than folded into "gate count." The remaining
125-code live surface is where the plan's rule ("every gate was almost
certainly added in response to a real incident... no check was removed when a
later one subsumed it") actually applies, and is what §2–§3 below analyze.

## 3. Subsumption findings

**The dead-path/live-path split above is itself the largest subsumption
finding**, and it is a clean one under the plan's own rule (§3: "no check was
removed when a later one subsumed it"). The v3 rewrite subsumed the *entire*
v1 and v2 contract — same invariants (fee replay, gas-stage replay, mark
lineage, accounting), stronger evidence (fork-estimated 7-stage replay
instead of manually-registered "validated" evidence), same completion
semantics (append a mark, an accounting snapshot, a fee-evidence row) — and
the v1/v2 code was never removed. Unlike the checks the plan's §3 discusses,
this is not "two gates checking the same thing at different times for a
legitimate TOCTOU reason." It is one generation of the entire operation
sitting unreachable next to its replacement. Concretely proposable for
removal, each against the incident it was presumably for:

- `paper-close-convert.ts` (both functions), `store.ts` `replayPaperCloseConvert`,
  `closeConvertGasScopeV2`, `prepareTrustedPaperCloseConvert`,
  `completeTrustedPaperCloseConvert`: no incident record found that these
  specifically were added for (they predate the incident-review corpus in
  `docs/reviews/`, per the commit log — `c76920b` "Add inert paper
  close-convert preflight contract" is the oldest close-convert commit found
  and is already the v3 lineage). They were superseded, not incident-driven,
  so the plan's "name the incident" test doesn't apply the same way — the
  argument for removal is subsumption by construction (v3 replaces v1/v2
  end-to-end), not "a later gate covers this one."
- `assertPersistedPaperCloseConvertGasEvidence`, `registerPaperCloseConvertGasEvidence`,
  `selectRegisteredPaperCloseConvertGasV2`, and the two CLI scripts that call
  them: this is a "validated/realized gas evidence" side-channel for a gas
  contract (`PAPER_STATIC_CONVERT_GAS_PATH_V2`, non-prestate) that the live
  system no longer produces or consumes for completion. It is not obviously
  incident-driven either — it looks like tooling built for a promotion
  workflow (fork-estimated → operator-validated) that v3's prestate model
  made unnecessary by making every stage's evidence self-verifying against
  the pinned block (`sourceReplayHash`, `gasScopeHash`, `gasSequenceHash`).
  **Caveat:** I could not determine from source alone whether these two CLI
  scripts are still exercised by an operational runbook outside this
  repository. `docs/operations/static-paper-mvp.md` does not mention them by
  name (verified by grep). This should be confirmed with the operator before
  deletion, not assumed.

**Within the live (v3) 125, three genuine TOCTOU brackets were found — not
duplication:**

- `paper_close_convert_v3_source_stale` is checked twice against the *same*
  180 s-from-block-timestamp bound: once inside the shared verifier
  (`terminal-replay-verifier.ts:195`, run by both admission's `verifyTerminal`
  and the worker's `verifyPaperStaticCloseConvertTerminalForWorker` call) and
  once more inside `completeTrustedStaticPaperCloseConvertV3`'s own
  transaction (`store.ts:4711`). Between those two checks sits an entire `FOR
  UPDATE`-locked transaction doing further reads. This is the same pattern
  the plan already validated for open/close_retain (category 1): a recheck at
  commit time against state that can genuinely move between review and
  commit. Legitimate, not redundant — **but see §4**: the reason this bracket
  matters here in a way it doesn't for its siblings is that the *first* check
  and the *second* check are usually not seconds apart, as they are for open;
  they can be minutes apart, because a full fork replay sits between them.
- `paper_close_convert_v3_source_not_canonical` (or its non-v3 analogue) is
  checked at preview build, at admission (`store.ts:2854`), and at worker
  completion, both before (`store.ts:4714`) and after (`store.ts:4783`,
  `paper_close_convert_v3_source_changed_during_completion`) the accounting
  writes. Four checks of "has this exact block reorged" across one operation.
  Each one guards a different window (before vs. after the DB writes in the
  same transaction is the same defence-in-depth pattern category 1 already
  covers for open); this is not excess by the plan's own standard.
- The fee-carry chain (group C) is independently rebuilt and reverified by
  `readStaticPaperCloseConvertFeeContext`/`replayEphemeralStaticPaperCloseConvertFees`
  at all three stages (build, admission, worker) — not a TOCTOU pair but a
  TOCTOU *triple*, each one a full O(marks-since-open) replay capped at 100
  marks. Each occurrence is individually justifiable (the fee chain really
  can move between any two of the three stages, since marks keep getting
  written every 1–2 minutes by other maintenance passes). The concern is not
  that any one of the three checks is wrong; it's that **three chances to hit
  the same intermittent failure mode** (indexer lag against a moving cursor —
  exactly what `d68827c` fixed) compounds probability of failure roughly
  three-fold, for a check that has already caused a confirmed, named
  production incident. See §4.

**One true subsumption candidate inside the live surface:**
`paper_close_convert_v3_preview_evidence_changed` (`store.ts:2792`) checks, at
admission, that the *preview's stored evidence blob* (`gasReportHash`,
`gasScopeHash`, `feeCarryHash`, etc. — all derived fields) matches the current
model. But admission has already, immediately before this, independently
recomputed the entire terminal model via `verifyTerminal` (a full fork
replay) and compared its hashes to the model
(`paper_close_convert_v3_terminal_verification_unavailable`, `store.ts:2688`).
The full-replay comparison is strictly stronger than the evidence-blob
comparison — if the fork replay reproduces the exact same `modelHash`,
`feeReplayHash`, `intervalHash`, `gasReportHash`, and `quoteHash`, the derived
evidence fields (which are hashes *of* those same values) cannot differ. This
looks like genuine redundancy, not a TOCTOU pair, since both checks read the
*same* `preview.evidence` row at the *same* point in the *same* transaction.
**This is a candidate for removal**, but the case is thin: I did not find an
incident record naming it, and removing it saves nothing on latency (it's a
hash comparison inside an already-open transaction) — the only benefit would
be maintainability, which is a real but small argument. I would not spend the
plan's remaining budget on it.

## 4. Why it has never completed

**Distinguishing structural from unlucky is the point of this section, so
the claim is bounded precisely: the v3 design requires the same expensive
owned-fork replay to succeed three independent times against windows that
share a single origin timestamp, and the measured cost of one replay already
consumes most of one window. That is a structural property of the design,
not a run of bad luck — and it is independently corroborated by a real
production run.**

### 4.1 The three replays

The owned-fork 7-stage sampler (`samplePaperCloseConvertPrestate`,
`paper-close-convert-prestate-sampler.ts`) — the same routine that the plan's
§4b measured taking ~90% of a 43–47 s *open* setup preview, for 6 stages —
is invoked in full, independently, at:

1. **Preview build** (`deployments.ts:205`, `owned_fork_sample` stage) —
   this is the 91–131 s the plan's table already measured.
2. **Admission** — `createStaticPaperCloseConvertAcceptance`
   (`paper-close-convert-runtime.ts:29`) is registered as the accept handler
   (`deployments.ts:411`). Its `verifyTerminal` callback calls
   `verifyPaperStaticCloseConvertTerminalForWorker`, whose `replayGasStages`
   callback calls `samplePaperCloseConvertPrestate` again (`runtime.ts:34–46`)
   — a second full owned-fork open, position restore, and 7-stage replay,
   run synchronously inside the HTTP accept request, *before* the database
   transaction that books the operation even opens.
3. **Worker completion** — `paper-operation-worker.ts:255`
   (`replayStaticCloseConvertV3Gas`) calls `samplePaperCloseConvertPrestate`
   a third time, against the *same* pinned model.source, after the operation
   has been claimed off the queue.

This is a real asymmetry with open/pause/resume/close_retain, not a
difference in degree. The plan's retracted category 2 established that open
performs exactly two fresh-frame reads (setup preflight, open preview) and
that everything after admission is a 1–2 s in-memory replay. **Close-convert
has not achieved that split.** Its admission step re-runs the single most
expensive operation in the entire system, synchronously, inside the accept
request.

### 4.2 Why that is fatal to the timing budget, not just slow

All three replays are checked against **wall-clock deadlines anchored to the
first replay's block timestamp**, not against a deadline that resets each
time:

- 180 s from `model.source.timestamp` (`prestate-sampler.ts:163`,
  `terminal-replay-verifier.ts:195`, `store.ts:4711–4712`, `store.ts:2852`).
- 120 s from `costs.gasPriceObservedAt`, which is captured once, near the end
  of preview build (`store.ts:2852`; gas price is read at
  `deployments.ts:229`, close to when the fork sample finishes, not
  refreshed at admission or worker time).
- The preview's own 60 s TTL (`preflight.ts:326`, `expiresAt=now+60_000`,
  where `now` is evaluated near the *end* of the ~91–131 s build, which is
  why the plan's measured operator window is 46–51 s and not closer to 180 s).

None of the replays refresh the block they read — they all re-read state *at
the original pinned `model.source`*, which is correct for replay integrity,
but means none of them buys back any of the clock. Arithmetic: build consumes
91–131 s of the 180 s window; admission's replay, doing comparable work, is
unlikely to be dramatically cheaper (the plan attributes ~90% of the
comparable *open* preview's latency to this exact sampler); worker completion
happens strictly after admission succeeds. Three replays of comparable cost
cannot fit inside one 180 s (or, more tightly, one 120 s gas-price) window
that the first replay alone already spends most of.

### 4.3 This is not a theoretical concern — it happened, and was correctly diagnosed as timing, not a bug

[`docs/reviews/static-paper-terminal-replay-followup-2026-09-27.md`](static-paper-terminal-replay-followup-2026-09-27.md)
records a live run (campaign `893514a2-e082-4a03-89ae-2e9e1b7f524c`) with
timestamps for every stage:

> Candidate captured at 16:50:30.308 UTC; gas observed at 16:51:18.381 UTC.
> Preview created at 16:51:23.828 UTC, acceptance persisted at 16:51:42.627
> UTC, preview expired at 16:52:18.381 UTC. Failure diagnostic at 16:52:39.359
> UTC, stage `terminal_gas_stage_replay`: source age 216,359ms...
>
> the eventual candidate was already 87 seconds old when captured, and
> preparation consumed another 48 seconds before the gas observation. Preview
> expiry and recovery then crossed the 180-second boundary. **Fast worker
> startup alone cannot resolve this run's timing constraint.**

That document independently reaches the same structural conclusion this
review reaches by reading the code — timing, not a defect in any one check —
and explicitly recommends against exactly the two "fixes" the plan's §3 later
retracts (extending the freshness limit, substituting acceptance time for
current time). It also records, in the same acceptance/worker cycle, a
*second* distinct failure mode: "second at `paper_conversion_prestate_fee_replay`
/ `AssertionError`" during an economic-worker-interruption test — consistent
with §3's finding here that the fee-chain replay (group C) is redone three
times and each redo is an independent chance to hit indexer lag.

The specific bug the task names — `paper_close_convert_fee_interval_gap`,
fixed in commit `d68827c` on 2026-09-30 — was a *trigger-condition* bug in the
retry loop (`readCanonicalPaperFeeInterval`'s 15 s settle wait only retried
on one of the two conditions that mean "indexer hasn't caught up yet"; the
other was misrouted to an immediate rethrow). Its commit message states the
mechanism precisely: "A mark is written every one to two minutes and its fee
interval can only be sampled once the indexer covers that block, a few
seconds later. Hitting the window aborted the whole maintenance pass..."
Fixing it removes one specific, previously-guaranteed-to-fail case. It does
not touch §4.1/§4.2: even with every fee-chain replay now retrying correctly
up to the 30 s `CURSOR_SETTLE_BUDGET_MS` (`paper-fee-replay.ts:35`, raised by
the plan's §3b), that 30 s is additional latency inside each of the three
replay attempts, not latency removed from the shared 180/120 s budget.

### 4.5 Structural vs. unlucky — the bounded claim

- **Structural:** three full-cost replays of the same routine, sharing one
  wall-clock origin, where one replay alone already consumes most of the
  available window. This does not depend on any specific bug; it follows
  from the measured latency numbers already in the plan (§1, §4b) and the
  call graph in §4.1. Fixing `paper_close_convert_fee_interval_gap` does not
  change it.
- **Not established as structural, but consistent with it:** every recorded
  attempt (the September 27 followup's four runs, the operator's two attempts
  on 2026-09-30) failed at a *different* named code, which is what you'd
  expect from a system with three independent, race-prone replay attempts

## 5. Proposed restated contract

**What convert genuinely needs**, restated from the invariant groups in §2,
independent of how many times each is currently checked:

1. The prestate replay (withdraw/collect → quote → swap → cleanup, 7 stages)
   must be proven to have actually executed, against the exact canonical
   block being converted, before the position is treated as exited. (Group D.
   Load-bearing — this is the paper analogue of the live RangeKeeper fork
   check the plan's §4c already validated as non-redundant with
   `eth_estimateGas`, for the same reason: it proves whole-sequence
   feasibility, not one transaction's gas.)
2. The fee-carry chain from open to the mark being converted must be
   complete and replay to the persisted carry. (Group C. Load-bearing —
   this is what stops converting against unearned or double-counted fees.)
3. The source block must not have reorged, and its independent reference
   price must still be within band, at the moment the terminal mark is
   booked. (Groups A/B, at exactly one point: booking. Load-bearing.)
4. The operation, preview, and prior mark must be exactly what was admitted
   — no interleaving operation, no stale preview, no changed profile/config.
   (Groups F/G/I/J. Load-bearing — this is the same idempotency/anchor
   category the plan's §2 already calls out-of-scope for the whole plan.)
5. The resulting accounting snapshot must project exactly the capital-out
   flows the model promised, chained correctly to the prior snapshot. (Group
   H. Load-bearing.)

**What a simpler implementation of that contract would look like:** the
minimum change consistent with §1–§4 is *not* pruning any of groups A–L on
their own merits — each was individually defensible when traced to its
invariant — but changing **how many times the expensive step (the 7-stage
fork replay and the fee-chain rebuild) runs before booking**, from three to
one:

- **Preview build** keeps the full replay (it has to — this is where the
  evidence is created).
- **Admission** (`acceptStaticPaperCloseConvertV3Operation`'s `verifyTerminal`)
  is the one to change. It currently re-runs the entire fork replay
  synchronously in the accept request. The open/pause/resume/close_retain
  precedent (plan §2, "category 2 withdrawn") is that admission should
  *replay from pinned* — recompute hashes from the already-persisted model
  and recheck the canonical anchors/reorg state, without re-executing the
  fork. Group F (preview/model integrity) already gives admission a hash
  comparison strong enough to catch a changed model; what admission does not
  need is to *regenerate* the evidence it's comparing against. The
  fork-replay-as-integrity-proof that groups D and C need only has to happen
  once *before* something irreversible is committed — and for paper, nothing
  is irreversible until the mark and accounting snapshot are written at
  worker completion. So the correctly-placed single re-verification point is
  worker completion, not admission.
- **Worker completion** keeps its full replay (this is the analogue of the
  live RangeKeeper's pre-broadcast check — the one place the plan's §4c says
  the fork simulation earns its cost is immediately before an action that
  can't be undone; for paper that's booking the terminal mark).

That change removes one of the three replays (admission's) and, by removing
it, removes one of the three independent chances to lose the 180/120 s
budget race and one of the three independent chances to hit fee-chain
indexer lag. It does not remove a single invariant from §2 — every group
still gets checked, once at build (to create it) and once at completion (to
re-verify before the irreversible write), which is exactly the
bracket-not-duplicate pattern the plan already validates elsewhere.

**What would be lost:** admission would move from "independently re-executed
proof, immediately before booking is queued" to "hash-verified replay-from-
pinned, immediately before booking is queued, with the independent
re-execution deferred to the worker." Between accept and the worker's actual
run, an operator would be trusting the preview's fork evidence for slightly
longer than they do today. Given that (a) the source-freshness and reorg
checks still run at admission unchanged, (b) the worker still independently
re-executes before anything is written, and (c) the plan's §4c finding that
this exact class of check "authorizes a displayed estimate and an admission
limit," not "a real broadcast of real funds" — this looks like a small,
named cost for removing roughly a third of the timing pressure that §4
identifies as the operation's structural problem. I have not measured what
the resulting admission latency or completion rate would actually be; that
is the natural next step and is explicitly **not done here**, per the task's
analysis-only constraint.

**Separately, and lower-priority:** delete the dead v1/v2 machinery (§1, §3)
once the operator confirms the two CLI scripts aren't used by an external
runbook. That removes 87 of 212 codes and one of the 13 named files entirely,
with no behavior change, because nothing currently reaches any of it.
